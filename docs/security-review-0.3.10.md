# Проверка безопасности 0.3.10

Дата: 2026-11-13. Версия 0.3.10 (75), тестовый билд. Предыдущие отчёты: `docs/security-review-0.3.9.md`, `docs/security-review-0.3.8.md`, `docs/security-review-0.3.2.md`.

Проверялось: изменения 0.3.10 — подавление уведомлений на переднем плане, фоновый опрос сервера вместо опоры на SSE, уведомление о завершении прогона по отказу/ошибке из транскрипта, старт keep-alive при отправке промпта, закрытие клавиатуры перед выбором модели. Метод: чтение диффа, `npm audit`, статический скан секретов, прогон `check:versions`, `typecheck`, `test`, `test:coverage`.

## Новое поведение и его границы

| Изменение | Границы безопасности |
|---|---|
| `send()` не публикует ничего при `AppState === "active"` | Только условие показа; текст, канал и разрешения не изменились. Кнопка тестового уведомления вызывает `sendTest()` напрямую и намеренно обходит правило — иначе её нельзя было бы проверить на открытом экране. |
| Фоновый опрос каждые 5 с при наличии активного прогона | Работает только при `AppState !== "active"` и только для сессий, которые клиент уже считает запущенными (`sessionStatus` busy или оптимистичный `sending`). Это те же запросы, которые уже делает клиент: `permission.list`, `question.list(sessionID)`, `session.messages`, `session.active`. Новых эндпоинтов и полномочий нет, креденшелы берутся из того же клиента соединения. |
| Уведомление о завершении из транскрипта | Тело «completed» — заголовок сессии через `sanitizeBody`, тело «error» — `message.error.message` через `sanitizeBody`. Это то же правило, что в 0.3.2: только собственные данные пользователя, без путей, tool-вывода и команд. |
| Уведомления о новых формах/разрешениях из опроса | Тексты фиксированные (`notifications.titles.*`, `PERMISSION_NOTIFICATION_KEY`, `QUESTION_NOTIFICATION_KEY`) — заголовок вопроса и текст команды на экран блокировки не попадают. Дедупликация по id: форма, пришедшая и по SSE, и опросом, даёт одно уведомление. |
| `setKeepAlive(true)` при отправке промпта | Тот же неэкспортированный foreground-сервис и те же разрешения, что в 0.3.8; меняется только момент старта. Постоянное уведомление содержит фиксированные строки i18n. |
| `Keyboard.dismiss()` перед выбором модели | Локальный вызов UI, сетевых или файловых эффектов нет. |

## Проверено, изменений не потребовалось

- **Новых разрешений нет.** `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_DATA_SYNC`, `POST_NOTIFICATIONS` — из 0.3.8/0.3.9; `blockedPermissions` по-прежнему только `SYSTEM_ALERT_WINDOW` (есть тест).
- **`AppState` в сторе** — единственный новый импорт `react-native` в `src/stores/events.ts`; подписка ставится один раз (`appStateWatchInstalled`), слушатель не хранит ссылок на пользовательские данные.
- **Фоновый таймер** снимается на `active` и в `connect()`, поэтому в foreground опроса нет; при отсутствии активных прогонов тик сразу выходит — сеть не трогается.
- **Дубли уведомлений.** SSE-обработчики и `refreshPending` пишут в один и тот же стор, проверка «уже есть такой id» стоит перед уведомлением; завершение прогона дополнительно ограничено 15-секундной отметкой на сессию, которая сбрасывается новым `busy`.
- **404 при ресинке** по-прежнему не уведомляет (сессия удалена — это не завершение прогона).
- **Секреты:** статический скан отслеживаемых файлов чист (единственное совпадение — фиктивный `AIzaSyDummyGoogleKeyValue…` в `custom-provider.test.ts`).

## `npm audit`

**3 записи, все moderate** — `minimatch` 10.2.6 в `expo → @expo/fingerprint` (GHSA-g3hv-75wg-m249). Сборочная цепочка, в рантайме APK не используется. Осознанно принятый остаток, как в 0.3.0–0.3.9.

## Известные остатки (приняты)

- **Уведомления приходят только в фоне.** Если пользователь смотрит на чат, сигнала нет — по его же просьбе; ответ виден в транскрипте.
- **Опрос раз в 5 секунд** идёт, пока приложение в фоне и прогон активен. Батарея: 4 запроса к локальному/LAN-серверу за тик; при отсутствии прогонов — ноль.
- **Прогон, начатый не с этого устройства** (терминал, другой клиент), не отслеживается: клиент не знает о нём и не опрашивает. Расширение сознательно не делалось — иначе телефон начнёт уведомлять о чужих сессиях.
- **`FOREGROUND_SERVICE_DATA_SYNC` ограничен 6 часами в сутки на Android 15+** — для агентских прогонов достаточно.
- **Пароль по `http://`, `usesCleartextTraffic=true`, отсутствие pinning** — без изменений.

## Не проверялось

Фактическая доставка на заблокированный телефон и поведение 5-секундного таймера под Doze/App Standby (локального Android SDK нет): проверка — установка APK, запуск сессии и сворачивание приложения. iOS: поллинг тот же, foreground-сервиса нет.
