# Проверка безопасности 0.3.9

Дата: 2026-11-12. Версия 0.3.9 (74), тестовый билд. Предыдущие отчёты: `docs/security-review-0.3.8.md`, `docs/security-review-0.3.2.md`, `docs/security-review-server-api.md`.

Проверялось: изменения 0.3.9 — отказ от глушения уведомлений на переднем плане, channel-aware trigger, логирование причин отказа, статус системного разрешения и кнопка тестового уведомления в настройках. Метод: чтение диффа и кода `expo-notifications` 58.1.9 (JS и Android), `npm audit`, прогон `check:versions`, `typecheck`, `test`, `test:coverage`.

## Исправлено

| # | Severity | Проблема | Исправление |
|---|----------|----------|-------------|
| 1 | MED (доступность) | В 0.3.8 осталось правило «приложение активно и открыт тот же чат → не уведомлять». Пользователь проверял уведомления, не сворачивая приложение, поэтому в шторке был только постоянный сервис, а completed/question/error не приходили. | Правило удалено: `send()` доставляет всё, что включено в настройках. `src/lib/notifications-send.test.ts` прогоняет настоящий модуль против фейкового `expo-notifications` и проверяет доставку при активном приложении. |
| 2 | LOW (корректность) | `trigger: null` заставляет нативный `BaseNotificationBuilder` игнорировать запрошенный канал: `content.channelId` на Android не читается вовсе, уведомление уходит в `expo_notifications_fallback_notification_channel`. Настройки канала приложения (`prompts`, HIGH) не применялись. | Channel-aware trigger `{channelId: "prompts"}` — единственная форма, которую native понимает как «доставить сейчас в этот канал». Зафиксировано тестом. |
| 3 | LOW (диагностируемость) | Любая причина отказа (нет разрешения, нативная ошибка) была неотличима от «уведомлений нет»: `send()` вызывается без `await` из обработчиков событий, отклонение промиса не видно. | `send()`/`granted()`/`setup()` не отклоняются: причина пишется в лог-буфер (`log.info`/`log.error`, попадает в отчёт диагностики), а `deliver()` ловит ошибку нативной отправки. |

Кнопка тестового уведомления показывает фактический результат. |

## Что проверялось в связи с этим

- **Новых разрешений нет.** Используются уже объявленные `POST_NOTIFICATIONS` (runtime) и `FOREGROUND_SERVICE(_DATA_SYNC)` из 0.3.8. `blockedPermissions` по-прежнему только `SYSTEM_ALERT_WINDOW`, есть тест.
- **Тестовое уведомление** содержит только фиксированные строки из i18n (`settings.notifications.test.title/body`), без данных сессии, сервера и пользовательского ввода.
- **Статус разрешения** — `Notifications.getPermissionsAsync()`, значение только сравнивается с `"granted"`; в UI выводится одна из двух локализованных строк.
- **`Linking.openSettings()`** открывает экран настроек самого приложения (`ACTION_APPLICATION_DETAILS_SETTINGS` для текущего пакета в реализации RN), а не произвольный URL — внешний ввод туда не попадает.
- **Тексты уведомлений о permission/question** остаются фиксированными ключами i18n без интерполяции; completed/error — заголовок сессии и текст ошибки через `sanitizeBody` (решение 0.3.2 не менялось).
- **Лог-буфер** — кольцо на 200 записей в памяти, уходит только с отчётом диагностики по действию пользователя; новых полей с секретами не добавлено.
- **Секреты:** статический скан отслеживаемых файлов чист (единственное совпадение — фиктивный `AIzaSyDummyGoogleKeyValue…` в `custom-provider.test.ts`).

## `npm audit`

**3 записи, все moderate** — `minimatch` 10.2.6 в `expo → @expo/fingerprint` (GHSA-g3hv-75wg-m249). Сборочная цепочка, в рантайме APK не используется. Осознанно принятый остаток, как в 0.3.0–0.3.8.

## Известные остатки (приняты)

- **Уведомление в foreground** теперь показывается и когда пользователь смотрит на тот же чат. Это осознанный выбор в пользу «уведомление лучше пропущенного», категорию можно выключить в настройках.
- **Разрешение, выданное в системе, приложение не отзывает** — это делает только пользователь.
- **Постоянное уведомление keep-alive** во время прогона — цена foreground-сервиса (см. 0.3.8).
- **Пароль по `http://`, `usesCleartextTraffic=true`, отсутствие pinning** — без изменений.

## Не проверялось

Фактическая доставка на устройстве (локального Android SDK нет): проверка выполняется установкой тестового APK и кнопкой «Отправить тестовое уведомление», которая печатает результат. iOS: канал и channel-aware trigger не используются, ветка `Platform.OS !== "android"` возвращает `trigger: null`.
