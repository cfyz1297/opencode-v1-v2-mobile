# Проверка безопасности 0.3.13

Дата: 2026-11-13. Версия 0.3.13 (78), тестовый билд. Предыдущие отчёты: `docs/security-review-0.3.12.md`, `docs/security-review-0.3.11.md`, `docs/security-review-0.3.10.md`.

Проверялось: изменения 0.3.13 — `KeepAliveService` переведён с обычного `Service` на `HeadlessJsTaskService` (headless JS-задача `KeepAliveBackground`), регистрация и завершение этой задачи в `src/lib/keep-alive.ts`. Метод: чтение кода React Native (`JavaTimerManager.kt`, `HeadlessJsTaskService.kt`, `HeadlessJsTaskConfig.kt`), чтение диффа, `npm audit`, статический скан секретов, прогон `check:versions`, `typecheck`, `test`, `test:coverage`.

## Причина, установленная по исходникам RN

`JavaTimerManager.onHostPause()` ставит `isPaused = true`, а колбэк кадров снимается, пока `isPaused && !hasActiveTasks()`. Значит `setInterval` в фоне не работает вообще. Отсюда и «в фоне сессия не обновляется», и «уведомления приходят только после открытия»: JS был полностью остановлен, а на резюме проигрывался накопленный SSE-поток. Это объясняет поведение лучше любой из прежних гипотез (сеть, канал, разрешения) — и подтверждается логом: один тик сразу после сворачивания, затем 15 секунд тишины.

## Что изменилось и его границы безопасности

| Изменение | Границы безопасности |
|---|---|
| `KeepAliveService : HeadlessJsTaskService` | Тот же неэкспортированный сервис, тот же `FOREGROUND_SERVICE_DATA_SYNC`, то же постоянное уведомление. Новый эффект — сервис держит **headless JS-задачу** и частичный wake-lock (`HeadlessJsTaskService.acquireWakeLockNow`), пока идёт прогон. Это осознанная плата за работоспособность фоновых уведомлений; задача завершается на `setKeepAlive(false)`. |
| `HeadlessJsTaskConfig(TASK_KEY, emptyMap, 0, true)` | `timeout = 0` — задача не завершается по таймауту (иначе RN убил бы React-инстанс посреди прогона); `allowedInForeground = true` — сервис стартует из переднего плана. Данные в задачу не передаются (`Arguments.createMap()` — пустая карта). |
| Регистрация `AppRegistry.registerHeadlessTask` | Регистрируется один раз за процесс, только ключ `KeepAliveBackground`; тело задачи ничего не делает, кроме ожидания разрешения промиса. Никаких входных данных, сети и файлов. |
| Завершение задачи на `stop()` | Разрешает все накопленные промисы → `hasActiveTasks()` становится ложным, таймеры снова могут быть приостановлены. Без этого приложение оставалось бы «активным» для RN навсегда (лишний расход батареи). |

## Проверено, изменений не потребовалось

- **Новых разрешений нет:** `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_DATA_SYNC`, `POST_NOTIFICATIONS` — из 0.3.8/0.3.9; `blockedPermissions` — только `SYSTEM_ALERT_WINDOW` (есть тест).
- **Сервис по-прежнему не экспортирован** (`android:exported="false"`), `onBind` возвращает `null`, входных точек из других приложений нет.
- **Уведомления**: те же фиксированные строки i18n для keep-alive; permissions/questions — фиксированные ключи без интерполяции; completed/errors — `sanitizeBody` (правило 0.3.2).
- **Сеть**: новых запросов нет. Headless-задача лишь разрешает уже существующему JS-коду (опрос `/api/session/active`, тот же клиент и авторизация) работать в фоне.
- **Секреты:** статический скан отслеживаемых файлов чист (единственное совпадение — фиктивный `AIzaSyDummyGoogleKeyValue…` в `custom-provider.test.ts`); gitleaks в CI.

## `npm audit`

**3 записи, все moderate** — `minimatch` 10.2.6 в `expo → @expo/fingerprint` (GHSA-g3hv-75wg-m249). Сборочная цепочка, в рантайме APK не используется. Осознанно принятый остаток, как в 0.3.0–0.3.12.

## Известные остатки (приняты)

- **Headless-задача и wake-lock живут только во время прогона** (от отправки до события завершения/превышения квоты). Вне прогона сервис остановлен, задача завершена.
- **`FOREGROUND_SERVICE_DATA_SYNC` ограничен 6 часами в сутки на Android 15+**; при исчерпании система остановит сервис, и фоновые уведомления деградируют (в логах будет видно отсутствие тиков).
- **`START_REDELIVER_INTENT`** (поведение базового класса): после убийства процесса система может перезапустить сервис и задачу; JS в этом случае стартует заново, состояние прогона восстанавливается обычным путём подключения.
- **Уведомление о завершении приходит для любой сессии на этом сервере**, включая запущенную из терминала.
- **Пароль по `http://`, `usesCleartextTraffic=true`, отсутствие pinning** — без изменений.

## Не проверялось

Работа `HeadlessJsTaskService` в bridgeless-режиме Expo SDK 58 на реальном устройстве (локального Android SDK нет): проверка — установка APK, прогон, сворачивание, затем блок диагностики в настройках (ожидаемые строки: `[keepalive] headless task running`, повторяющиеся `[watch] tick (background)`, `[notifications] completed: posted`). Поведение под Doze/App Standby. iOS: сервиса и задачи нет, ветка не менялась.
